# Domain Concepts

## Project

The top-level organizational unit. A project contains files, sets, processing results, and sources as a directed acyclic graph (DAG). Projects appear as nodes on the home page and serve as the entry point to the graph workspace.

- Created with: name, description, position (x, y for home page placement)
- Each project has its own graph view
- Projects can be deleted (destroys all contained nodes)
- Projects track storage size

**Verified from:** `src/api/client.js` (`createProject`, `deleteProject`, `getProject`)

## File

A document stored in the system. Files have:
- `@rid` — ArcadeDB record ID (e.g., `#21:5`)
- `type` — Semantic type assigned by backend (e.g., `image`, `text`, `ocr.json`, `ner.json`)
- `extension` — File extension
- `label` — Display name (mutable by user)
- `path` — Server-relative path to file content
- `description` — User-editable description
- `entities` — Linked entity/tag list
- `edited` — Object present if file has been quick-edited (contains `task` field)
- `ref` — Boolean flag; if true, file is a reference (not editable)
- `thumbnail_version` — Cache-bust token for thumbnail URLs

Files are nodes in the project graph. They can be processing inputs or outputs.

**Verified from:** `src/features/files/useQuickEdit.js`, `src/api/client.js`, `test/features/files/components.spec.js`

## Set

A collection of files within a project. Sets appear as graph nodes and can be:
- **Flat:** Simple list of files
- **Grouped:** Files organized by source/origin

Sets support:
- Pagination (10 files per page in graph view, 24 in standalone)
- ZIP export (async job with status polling)
- Batch processing (run a cruncher on all files)
- File upload directly into set (single or multiple files; multi-file upload is Set-only, never onto the main desk)
- Thumbnail generation for contained files

Once a Set has been used as the input of a batch cruncher run, it is **locked**: no more files can be
added to it. There is no mechanism to re-run or extend a finished batch to cover files added afterwards,
so the backend rejects uploads into an already-processed Set (`Graph.hasSetBeenProcessed`, checked in
the upload route) and the UI hides the upload button in favor of a warning (`panel/NodeTools.vue`'s `setLocked`,
backed by the `processed` flag on the Set's graph node data). See
[processing-crunchers.md](processing-crunchers.md#set-locking-after-batch-processing).

**Verified from:** `src/features/project/` (`graphModel.js`, `SetBrowser.vue`, `panel/NodeTools.vue`), `src/api/client.js`

## Source

An external data provider connected to a project. Known source types:
- `dspace7` — DSpace 7 repository
- `nextcloud` — Nextcloud file storage

Sources are created within a project and appear as graph nodes. They can be targets for batch processing.

**Verified from:** `src/features/project/nodes/index.js` (node types), `dialogs/CreateSourceDialog.vue`, `src/api/client.js`

## Entity (Tag)

A typed label that can be linked to files. The entity system provides:
- **Types:** Per user and shared by all their desks (`getEntityTypes()`); a tag always has a type. `Tag` is protected (machine autotag uses it) and a type can only be deleted when it has no tags
- **Instances:** Created per type with a label
- **Links:** Entities are linked to files (many-to-many), backed by the `TagLink` type on the backend (see
  MessyDesk's [graph-data-model.md](../../MessyDesk/wiki/architecture/graph-data-model.md))

The UI calls them "Tags" in the header tabs but "Entities" in the code and API. Tags can be manual
(`created_by: 'user'`, "human tags") or machine-generated by a processing service's Autotag (`created_by: 'machine'`).

**Human tags belong to desks.** A human tag lives in the vocabulary of the desks that have it (backend
`DeskTag`). Creating one always needs a desk (`project_rid` is required by `POST /api/entities` and
`/api/tags`) and happens only in Tag admin: `AddTagDialog` (opened from `TagAdminDialog`) takes the current
`deskRid` and, in the global Tags view, asks which desk. `FileTagsTool` (file viewer, desk from the route) and
`TagPickerField` (desk injected by `CruncherPicker` through `crunchers/deskScope.js`) only suggest that desk's tags. A tag can be
shared by several desks (import); renaming it changes it in all of them. On the Tags page, with several tags selected, a toggle chooses files with any of them (default) or with all of them (`state.match` in `useTags`). In the global view the tag chips show
the desk names (`deskHint(tag)` from the `desks` of `GET /api/entities/by-type/:type`).

**Tags screen** (`features/tags/TagsPage.vue`): the plain per-type list (Tag, Person, ...) only shows human
tags, real Autotag-created tags are browsed in their own "Machine tags" section grouped by
`(service_id, task, model)` (`web.getMachineTags`, desk-scoped), and Faceted ROI-data results (see MessyDesk's
[glossary.md](../../MessyDesk/wiki/glossary.md)) are browsed in a separate "NER results" section that reads
each matching file's `ner.json` regions on demand (`web.getNerLabelGroups`/`getNerLabelMentions`) — there is
no separate region-scoped tag data model for that case. The list loading is shared with the picker in
`tags/tagLoaders.js` (`createTagLoaders`, `createRoiLoader`).

**Tag admin** (`TagAdminDialog.vue`, the "Tag admin" button of the Tags screen; a dialog, not a route): a
searchable, paged table of human tags (`GET /api/tags/admin`) with label, type, files, desks and, only when
someone other than the signed-in user made tags, "Created by". Actions: create (`AddTagDialog`), rename,
import from another desk (`TagImportDialog`, `POST /api/projects/:rid/tags/import`), "Remove from this desk"
(desk view) and "Delete everywhere" (global view only). Rename, remove and delete go through
`TagActionDialog`, which first reads `GET /api/entities/:rid/usage` and warns with the file count and the other
desks affected (`tagAdmin.js` `actionText`); a rename rejected with 409 shows the backend message. State and
flows are in `useTagAdmin.js` (`useTagAdmin`, `useTagAction`) and `useTagImport.js`.

**Tag types** (`TagTypesDialog.vue`, `useTagTypes.js`, the "Tag types" button of Tag admin): table of the user's
types with a colour chip and the number of tags in all desks, an "Add type" form (name, optional colour; the
backend's 400/409 messages are shown) and delete with a confirmation. `Tag` has no delete action (tooltip: used by
machine tags) and a type with tags has it disabled ("Delete its N tags first", `typeDeleteBlock`). After a change
the admin table reloads and the Tags screen is told (`changed`). `AddTagDialog` loads the types when it opens,
starts with `Tag` (else the first type, `defaultType`), cannot clear the type, and keeps Create disabled until
desk, type and label are set.

**Tag picker** (`features/tags/TagPicker.vue`, used by the cruncher tag filter `TagFilterDialog`): compact
and fixed to one desk: search box, selected chips, collapsed groups of human tags by type (paged), machine tags
by run and a separate collapsed "Found in text (ROI labels)" section (`RoiLabelPicker.vue`,
`GET /api/tags/roi/labels`, grouped by run, counts, "Load more"). ROI labels are not tags: the filter sends
them as `selected_roi_labels: [{ service_id, task, model, label }]` next to `selected_entity_rids`
(`crunchers/tagFilter.js`). A failed ROI request (search index down) shows an error in that section only.

**Who tagged:** the file viewer's `entities[]` carry `tagged_by: [{ rid, name }]` (who attached a tag by hand);
`FileTagsTool` shows it as a tooltip on the chip and nothing for machine-only tags.

**Verified from:** `src/features/tags/`, `src/features/files/tools/FileTagsTool.vue`, `src/api/client.js` (entity/tag methods)

## ROI (Region of Interest)

Rectangular selections on images. ROIs:
- Belong to a file within the context of a set (scoped by image RID + set RID)
- Are stored with pixel coordinates and original image dimensions
- Can be used as input for targeted processing (e.g., OCR a specific region)
- Have their own graph node type (`roi-set`)

**Verified from:** `src/api/client.js` (ROI methods), `src/features/project/useOpenNode.js` (ROI set handling)

## Cruncher/Process

A processing operation that transforms or analyzes files. See [processing-crunchers.md](processing-crunchers.md) for details.

## ServiceGroup

Admin-managed entity (`id`, `name`, `description`, `logo`) formalizing the `service_groups` values used
in `service.json` descriptors and on `User.service_groups` to gate which users can use a
service/task. Managed from the admin-only Service groups tab of the Admin page (`features/admin/ServiceGroupsTab.vue`); user membership is
edited inline from the Users tab in the same component. See the backend
[glossary](../../MessyDesk/wiki/glossary.md) and
[service-descriptor-format.md](../../MessyDesk/wiki/service-descriptor-format.md#service-groups) for
the full model, including the logo upload/resize flow.

## RID (Record ID)

OrientDB-style identifiers in format `#cluster:position` (e.g., `#21:5`). The frontend consistently strips the `#` prefix when embedding in URLs. The `@rid` field on returned objects always includes the `#`.

**Verified from:** `src/api/client.js` (all methods use `.replace('#','')`)

## Graph Relationships

The backend uses a directed graph (ArcadeDB). Key relationship patterns visible from the frontend:

- Project → File (contains)
- Project → Set (contains)
- Project → Source (has source)
- File → File (processing output, via Process node)
- Set → File (contains, with optional source grouping)
- Entity → File (tagged with)
- Process → File (produces)

**Inferred from:** `src/features/project/useOpenNode.js`, `nodeKinds.js` (`roiSourceNode`), `src/api/client.js`
